## Repository-specific records

### D26 — Melodyfire: the public experience of a coherent creative practice

**Use when:** When designing my portfolio, its narrative/navigation, services/shop, CMS, interactive proof, art worlds, or applications.

[Recovered intent] Melodyfire brings together generative art, regenerative/civic work, shaders, children's illustration, UI systems, prompt tools, services, and digital products. The current README records Aurora, Solarpunk Grimoire, and Holographic modes; Clash Display/Satoshi; a mandala hero; hash routes; Supabase-backed data; and storefront integrations.

[Design DNA] Preserve a recognizable authorial entry and clear doors into work, art, tools, services, and stories. Different portals may have distinct atmospheres while navigation, contribution, and evidence remain legible. A recruiter, client, collaborator, and buyer need different information depth.

[Observed boundary] README counts/routes, live deployments, product/pricing records, checkout behavior, and database protection were not browser-verified here. Current source includes application-specific proof assets, so the portfolio should make existing work easy to see before adding more systems.

[Repair resolution — proposed] Use project records with role/contribution, visual proof, intent, implementation state, source, and next action. Separate CMS editing from public read surfaces. Reconcile hash routes/deep links, mobile media presentation, loading/failure, and stale offer links. Do not claim a connected table or checkout label establishes secure production commerce.

[Reimagined horizon] A portfolio as studio atlas: strong visual work, explicit mechanisms, concise case stories, selectable deeper process, useful offers, and connected creative worlds. “Completion beats invention” should mean completing this experience while preserving its wider cultural/creative ambition.

[Carry-forward test] A person arriving from a real role/client brief can identify relevant work, inspect a visible demo, understand my contribution and limitations, and reach the right next action on mobile and keyboard.

## Practical continuation contract

1. Re-read current repository instructions and source before implementation. The baseline above identifies this publication, not a permanent execution HEAD.
2. Retain the full design horizon separately from the current demonstrator. Name what the demonstrator preserves, approximates, defers, or cannot prove.
3. Map tokens and controls to actual consumers with explicit units, ownership, accessible alternatives, and observable effect.
4. Complete the relevant interaction/error/cancellation states before promoting a reusable component.
5. Pair source/runtime checks with human correspondence review against the actual visual inspiration.
6. Keep proposed repairs unexecuted until a later implementation records its own revision, checks, and evidence.
